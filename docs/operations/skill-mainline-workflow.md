## 1. 角色与触发

### 1.1 默认角色

以**资深软件开发工程师**身份工作：结论先行、依据明确、术语统一、量化可判定；语气专业、自信、耐心；面向「帮助用户熟悉软件开发全流程」，每个阶段说明其存在理由与可观察产物。该角色在后续所有会话自动生效，无需重复声明。

### 1.2 触发条件（任一命中即自动调用本流程）

- 请求把某份 `SKILL.md` 落地为代码、PyRIT 原生实现或可纳入 CI 的交付物。
- 请求按「主线流程 / 全流程 / 工程链」推进某个技能或 backlog 条目。
- 已发布规格、工单或既有实现需要继续推进到下一阶段。

### 1.3 调用规则

1. **自动调用**：命中触发条件即按 §3 的 11 个阶段顺序推进，逐阶段加载对应技能，不等待逐条指令。
2. **顺序固定**：阶段编号即执行顺序。调换、合并、并行或跳过阶段均判定为不符合项，须回到原顺序重跑受影响阶段。
3. **`to-spec` 连续两次**：第 2 阶段与第 3 阶段各自独立执行、各自独立留痕，职责见 §3.2 与 §3.3；两次输出内容不同、版本号不同。
4. **`implement-spec` 与 `tdd` 的顺序**：本流程把实现置于测试驱动之前，属固定顺序。第 8 阶段产出接口完整、可编译、可验证的最小实现切片（tracer bullet）；第 9 阶段以规格为判据补齐红—绿—重构循环并收敛实现。测试暴露规格偏差时，退回第 8 阶段修正并重跑其门禁，再回到第 9 阶段。
5. **`pr-push-review` 名称映射**：已安装技能中不存在同名单一技能。该阶段是三个动作的复合阶段——`pr`（PR 正文模板）、`pre-push-review`（双轴语义评审与门禁复跑）、双通道推送与 PR 创建；内部次序见 §3.11。
6. **阶段门禁**：每阶段收尾执行 §2 的 G0；结论为 `PASS` 才进入下一阶段。

## 2. 阶段门禁协议 G0（每阶段收尾强制执行）

### 2.1 代码质量与工程标准基线

| 编号 | 基线 | 可判定依据与命令 |
|---|---|---|
| B1 | 技能解剖结构 | `GOVERNANCE.md` §4.2 五要素 + §4.4 登记；`python scripts/validate_skill.py` |
| B2 | 术语与决策一致 | `python scripts/check_glossary.py`；术语以 `GLOSSARY.md` 为准；与 ADR 冲突须显式标注（`docs/operations/domain.md`） |
| B3 | 语法与构建 | `python -m py_compile <变更的 .py>`；`python -m unittest discover -s tests -v` |
| B4 | 证据契约 | 每步 `tools/collect_evidence.py --step <prefix>-NN --strict`；`tests/test_<name>_evidence_contract.py` 断言三件套（命令 + 输出 + 截图）与 AI 交互日志（GOVERNANCE §6.1、§6.3） |
| B5 | 证据与 flag | flag 双通道一致（面板提交值 == 报告截图/正文）；访问证明 `whoami`/`id` + flag 同屏；技术读者可 copy/paste 逐步复现（GOVERNANCE §6.1、§6.2） |
| B6 | CI 门禁 | `docs/standards/CI-CD.md` S0–S4；本地与 CI 判定一致；存在业务代码时行覆盖率 ≥80%；Conventional Commits；受保护 `main` 仅经 PR 合并 |
| B7 | PyRIT 版本与对象图 | `pyrit==1.1.0`；权威索引 `docs/research/pyrit-canonical-references.md`；对象图统一采用 `pyrit.executor.attack` 下的 `*Attack` 与 `OpenAIChatTarget`；出现 `pyrit.orchestrator`、`*Orchestrator`、`AzureOpenAIChatTarget` 即登记为不符合项并修正 |
| B8 | 可追溯性 | 每条结论附一手来源；issue / PR / commit 互链（`Closes #x`）；推送按双通道约定各试一次即停；门禁记录留痕 |

### 2.2 收尾动作（5 步）

1. **列交付物**：逐项列出本阶段实际产出的文件、issue、命令与输出。
2. **逐项校验**：对照 B1–B8 与本节阶段的「验收标准」逐条判定；可自动化的检查须给出确切命令与输出摘要，人工检查须给出判据与结论。
3. **生成门禁记录表**，字段固定：

   | 编号 | 检查项 | 依据 | 实测结果（命令 + 输出摘要） | 判定 | 不符合项描述 | 修正要求（文件 + 位置 + 动作 + 复验命令） | 复验结果 | 结论 |
   |---|---|---|---|---|---|---|---|---|

   判定只取 `符合` / `不符合`；结论只取 `PASS` / `BLOCKED`。「基本完成」「大体符合」等表述不具判定效力。
4. **处置不符合项**：结论为 `BLOCKED` 时停留在当前阶段，按修正要求逐条改完后**重跑本阶段全部检查项**；以后续阶段补做替代修正视为不符合项。结论为 `PASS` 才进入下一阶段。
5. **留痕**：门禁记录写入本阶段交付物的「门禁记录」小节，并在对应 issue 评论区留一份摘要（阶段号、结论、不符合项数量、复验命令）。

### 2.3 持续校验

每阶段除校验自身交付物外，还须复核上游交付物未被本阶段改动破坏：上游验收标准与 B1–B8 中与本阶段相关的条目再次执行。复核失败时按 §2.2 第 4 步处置。

## 3. 主线 11 阶段

> 每阶段固定六个字段：**目标 / 输入 / 输出 / 关键活动 / 验收标准 / 阶段门禁**；另附**学习要点**，说明该阶段在工程链中的位置。

### 3.1 阶段 1 — `research`（调研）

- **目标**：用一手来源锁定实现所依赖的事实（API 名称、版本、行为边界），消除规格阶段的猜测。
- **输入**：目标 `SKILL.md`；`docs/research/pyrit-canonical-references.md`；官方仓库、官方文档、源码；`GOVERNANCE.md` 与相关 ADR。
- **输出**：`docs/research/<topic>.md` 一份，逐条结论附来源 URL 与版本；列「已核实 / 待核实 / 已排除」三类清单。
- **关键活动**：后台 agent 独立检索一手源 → 逐条回溯到拥有该事实的源 → 与 `SKILL.md` 的攻击路径逐项对齐 → 记录版本破坏性变更与禁用名称 → 标出实现前必须取证的核实闸。
- **验收标准**：① 每条结论可定位到官方 URL / 源码位置；② 版本号明确（`pyrit==1.1.0`）；③ 每条攻击路径都有对应对象映射；④ 待核实项逐条命名且给出取证方式；⑤ 文档落盘于 `docs/research/`。
- **阶段门禁**：B7、B8 全项；核对 G0 §2.2 表字段齐全；不符合项含「缺来源」「版本含糊」「攻击路径未映射」三类时逐条列出修正要求与复验命令。
- **学习要点**：观察「事实 → 规格」的传导；规格中出现未经一手源确认的 API 名称，即本阶段未达标。

### 3.2 阶段 2 — `to-spec` ①（行为规格 / What）

- **目标**：把 `SKILL.md` 声明的行为与攻击逻辑翻译成**做什么**的规格，形成可评审的用户视角描述。
- **输入**：目标 `SKILL.md`；阶段 1 调研文档；`GLOSSARY.md`；`docs/operations/issue-tracker.md`、`triage-labels.md`、`domain.md`。
- **输出**：issue tracker 中规格 v1（按 `to-spec` 模板七节），标签 `ready-for-agent`；保留 `SKILL.md` 原文为行为唯一来源，不改写。
- **关键活动**：探索代码库现状 → 用领域术语撰写 Problem Statement / Solution / 长清单 User Stories / Implementation Decisions / Testing Decisions / Out of Scope / Further Notes → 提出 seam（接缝）数量与位置并与用户核对 → 发布到 issue tracker。
- **验收标准**：① 七节齐全；② User Stories 覆盖 `SKILL.md` 全部攻击路径与质量门；③ 术语符合 `GLOSSARY.md`；④ 与 ADR 无静默冲突；⑤ Implementation Decisions 不含具体文件路径与代码片段；⑥ seam 提案已与用户核对并记录结论。
- **阶段门禁**：B1、B2、B8；逐条核对 v1 与 `SKILL.md` 五要素的一一对应关系；不符合项按「缺失路径 / 术语漂移 / seam 未确认 / 混入实现细节」列出修正要求。
- **学习要点**：本阶段只回答 What；出现文件路径或代码块即为规格层级越界。

### 3.3 阶段 3 — `to-spec` ②（工程规格定稿 / 可验证性与可拆解性收敛）

- **目标**：以 v1 为输入做第二次独立规格化，把「做什么」收敛为**可验证、可拆解、可交接**的定稿规格 v2；这是与阶段 2 不同的产物，不是重发一次 v1。
- **输入**：规格 v1 全文；阶段 1 待核实项的取证结果；代码库现状（`scripts/`、`tests/`、`tools/`、`.github/`）；GOVERNANCE §8.2 八项检查单；CI-CD S1–S4；`docs/research/pyrit-canonical-references.md`。
- **输出**：规格 v2 定稿（默认在 v1 同一 issue 以 `## 工程规格定稿 (v2)` 追加，保留 v1 全文并附 v1→v2 差异清单；若新建独立 issue，须在 v1 标注被取代并双向互链）；含逐条验收条件、测试决策、门禁映射、风险与核实闸。
- **关键活动**：逐条审查 v1 User Stories 的可判定性 → 把不可判定的描述改写为布尔验收条件 → 补齐 Testing Decisions（只测外部行为、列既有参考测试）→ 把 CI 门禁映射到每条验收条件 → 收敛 seam 决策与对象图 → 记录 v1→v2 差异及理由 → 发布并留痕。
- **验收标准**：① 每条 User Story 有对应布尔验收条件；② 每条验收条件指向具体检查命令或人工判据；③ 待核实项已关闭或转为带取证方式的核实闸；④ 差异清单逐条可追溯；⑤ 规格中不存在两套互相冲突的「当前规格」；⑥ 与阶段 2 输出内容不同且版本号递增。
- **阶段门禁**：B1、B2、B6、B7、B8；额外执行 §2.3 上游复核（v1 未被破坏）；v1 与 v2 并存时核对取代标记与互链完整。
- **学习要点**：两次 `to-spec` 的分工是「行为描述」与「可验证性收敛」；第二次的价值在于把模糊表述变成可执行判据，这是拆工单的前提。

### 3.4 阶段 4 — `to-tickets`（工单拆解）

- **目标**：把 v2 拆成可独立交付、可并行判定的垂直切片（tracer bullet），并显式声明依赖。
- **输入**：规格 v2；`docs/operations/issue-tracker.md` 的 sub-issue / blocking 约定；既有工单编号。
- **输出**：父工单 + 每攻击路径一张子工单 + 证据契约工单；每张工单含目标、验收条件、阻塞边、验证命令。
- **关键活动**：按攻击路径切分 → 每片保留一条端到端可运行链路 → 用原生 `blocked-by` 声明依赖（或按约定回退为 `Blocked by: #n` 文本）→ 父工单聚合进度 → 记录工单号与依赖图。
- **验收标准**：① 每条 v2 验收条件至少被一张工单覆盖；② 每张工单可单独验收；③ 阻塞边可在 tracker 中查询；④ 工单标题与 `GLOSSARY.md` 术语一致；⑤ 无环形依赖。
- **阶段门禁**：B2、B8；逐条执行覆盖矩阵核对；不符合项含「验收条件未覆盖」「阻塞边缺失」「依赖成环」。
- **学习要点**：观察规格到可执行单元的转换；工单粒度以「能独立跑出一条证据链」为准。

### 3.5 阶段 5 — `triage`（分类定级）

- **目标**：判定每张工单由 agent 还是人工承接，并补齐 agent 就绪所需的上下文。
- **输入**：全部新工单；`docs/operations/triage-labels.md` 五标签映射；`docs/operations/issue-tracker.md` 的 PR-as-request 开关。
- **输出**：每张工单的规范标签、分类理由、`ready-for-agent` 工单的 agent brief（目标 / 输入 / 约束 / 验收 / 验证命令）。
- **关键活动**：按五标签状态机流转 → 核验信息完整性 → 对目标端点凭据、CI secrets 等需人工项标 `ready-for-human` → 对信息不足项标 `needs-info` 并列出所缺信息 → 为 `ready-for-agent` 工单写 brief。
- **验收标准**：① 每张工单恰有一个规范标签；② 每个 `ready-for-agent` 工单含完整 brief；③ 人工项与 `ready-for-human` 一一对应并记录依据；④ 分类结论与理由同步留痕在 issue。
- **阶段门禁**：B8；核对标签字符串与映射表一致；`ready-for-agent` 但缺 brief 判为不符合项。
- **学习要点**：分类是「可自动化边界」的判定；brief 的质量决定后续实现是否需要返工。

### 3.6 阶段 6 — `codebase-design`（模块与接口设计）

- **目标**：确定深层模块边界与 seam 位置，使实现可测试、可注入、对 agent 可导航。
- **输入**：规格 v2；`to-tickets` 工单；现有目录与 `tools/collect_evidence.py` 边界；`codebase-design` 的深层模块词汇；阶段 2 已确认的 seam 提案。
- **输出**：设计记录（模块职责、公开接口、依赖方向、seam 清单、注入点、对象图构造收敛位置），落盘于规格 issue 或设计文档。
- **关键活动**：复用既有 seam → 新 seam 数量压到最少并置于最高层 → 定义公开入口与可注入依赖 → 明确 `pyrit` 延迟导入与测试假后端策略 → 记录权衡与被否决方案。
- **验收标准**：① seam 数量与位置明确且与阶段 2 结论一致；② 每个公开接口有职责、输入、输出、错误行为描述；③ 依赖方向单向；④ 测试替身可替换外部依赖；⑤ 与 ADR 冲突项已显式标注。
- **阶段门禁**：B2、B7、B8；核对设计不含 `pyrit.orchestrator` 等旧版对象；seam 数量增加时须记录理由。
- **学习要点**：设计决定测试成本；观察「接口少、实现深」如何减少后续变更面。

### 3.7 阶段 7 — `domain-modeling`（领域术语建模）

- **目标**：把实现引入的新概念纳入唯一术语基准，消除代码、规格、报告之间的语义漂移。
- **输入**：规格 v2、设计记录、`GLOSSARY.md`、`docs/governance/adr/`、PyRIT 实现层词汇清单。
- **输出**：`GLOSSARY.md` 增补条目；必要时新增 ADR；术语映射表（SKILL.md 概念 ↔ PyRIT 对象 ↔ 代码标识符）。
- **关键活动**：枚举新术语 → 与既有条目比对并归一 → 为每个术语写定义、禁用同义词、来源 → 记录需要重新开启的 ADR → 执行术语检查器。
- **验收标准**：① 映射表覆盖规格与设计中的全部新概念；② `GLOSSARY.md` 条目含定义与来源；③ `python scripts/check_glossary.py` 通过；④ ADR 编号连续、冲突显式标注。
- **阶段门禁**：B1、B2、B8；`check_glossary.py` 输出须附在门禁记录中。
- **学习要点**：术语统一是 CI 可检查的工程约束，不是文案润色；本阶段未完成会阻断后续验收。

### 3.8 阶段 8 — `implement-spec`（按规格实现）

- **目标**：按 v2 + 工单产出接口完整、可编译、可验证的最小实现切片，并保持与 `SKILL.md` 行为一致。
- **输入**：规格 v2、`ready-for-agent` 工单与 brief、设计记录、`GLOSSARY.md`、`docs/research/pyrit-canonical-references.md`。
- **输出**：实现代码（模块、对象图构造、公开入口）、必要的配置与依赖声明、每步证据片段；变更清单。
- **关键活动**：按工单逐片实现 → 对象图统一采用 `pyrit.executor.attack` 的 `*Attack` 与 `OpenAIChatTarget` → 外部依赖走注入点 → 每步调用 `collect_evidence.py --step <prefix>-NN --strict` → 保持 `SKILL.md` 为行为唯一来源 → 记录实现与规格的对应矩阵。
- **验收标准**：① 每条 v2 验收条件有对应实现位置；② `py_compile` 通过；③ 对象图符合 B7；④ 每步证据三件套齐全且可 copy/paste 复现；⑤ 无硬编码凭据；⑥ 变更清单与工单一一对应。
- **阶段门禁**：B1、B2、B3、B4、B5、B7、B8 全项；门禁记录须含每条命令的输出摘要。
- **学习要点**：实现阶段的产出必须**可验证**；本阶段只交付最小切片，完整测试与收敛在阶段 9。

### 3.9 阶段 9 — `tdd`（测试驱动开发）

- **目标**：以 v2 为判据补齐红—绿—重构循环，用测试锁定外部行为并收敛实现。
- **输入**：规格 v2 验收条件、阶段 8 实现、`tests/` 既有夹具、`docs/standards/CI-CD.md` S2 要求。
- **输出**：新增 / 修订的测试用例（标准库 `unittest`）、证据契约夹具、红→绿→重构三轮记录、覆盖率数据。
- **关键活动**：为每条验收条件写一个失败用例（红）→ 最小改动使其通过（绿）→ 重构并复跑（重构）→ 补 `tests/test_<name>_evidence_contract.py` 断言每步契约 → 运行全量测试与覆盖率 → 测试暴露规格偏差时退回阶段 8 修正并重跑其门禁。
- **验收标准**：① 每条验收条件有对应测试；② 红阶段有实际失败输出留痕；③ 全量 `unittest` 通过；④ 存在业务代码时覆盖率 ≥80%；⑤ 只测外部行为，不断言实现细节；⑥ 本地与 CI 判定一致。
- **阶段门禁**：B3、B4、B6、B8 全项；附全量测试输出与覆盖率数字；覆盖率不足时列出未覆盖分支与修正要求。
- **学习要点**：「红」的可信输出是测试有效性的证据；测试暴露偏差后的回退动作体现阶段门禁的闭环性。

### 3.10 阶段 10 — `code-review`（双轴代码审查）

- **目标**：相对固定基线，独立审查 Standards（编码规范）与 Spec（规格忠实度）两条轴，输出并列结论。
- **输入**：`git merge-base origin/main HEAD` 固定点之后的 diff；规格 v2 与工单；`docs/standards/CI-CD.md`、GOVERNANCE §8.2、`GLOSSARY.md`、`AGENTS.md`。
- **输出**：双轴并列报告（每轴发现数、最严重项、逐条分类：硬违规 / 判断项）、修复清单、复跑结果。
- **关键活动**：固定基线并确认 diff 非空 → 并行子 agent 分别审查两轴，不合并、不重排 → 逐条分类 → 硬违规先修复并复跑门禁 → 判断项记录为改进项 → 复跑 §2.3 上游复核。
- **验收标准**：① 两轴报告并列且各自结论完整；② 每条发现带文件位置与分类；③ 硬违规数量为 0；④ 规格覆盖矩阵无遗漏；⑤ 门禁套件全绿。
- **阶段门禁**：B1–B8 全项；附双轴发现数与最严重项；硬违规未清零时结论为 `BLOCKED`。
- **学习要点**：两轴分离可区分「代码写得对不对」与「做的是不是要求的」；判断项不阻断交付，硬违规阻断。

### 3.11 阶段 11 — `pr-push-review`（PR 与推送前评审复合阶段）

- **目标**：完成推送前语义级双轴评审、PR 正文、双通道推送与 PR 创建，衔接 CI 门禁。
- **输入**：阶段 10 全绿结论、工作树与分支 commits、远端 `origin/main` 基线、规格 v2、`.github/PULL_REQUEST_TEMPLATE.md`、双通道推送约定。
- **输出**：`pre-push-review` 双轴报告与门禁结果行、`pr` 模板正文（Summary / Evidence / Merge Danger）、PR 链接与编号、CI S1–S4 状态、推送结果记录。
- **关键活动**（内部次序固定）：
  1. `pre-push-review`：取远端基线 → 确定 diff 模式 → 识别规格源与标准源 → 并行双轴评审 → 分类发现 → 按人工确认批次修复 → 复跑门禁套件 → 最多 3 轮收敛 → 输出 PR 要素。
  2. `pr`：按模板写 PR 正文，Summary 用最小可视化（树 / diff / 调用链 / Mermaid），Evidence 给出改前改后证据，Merge Danger 标注单向门 / 双向门与影响半径；正文含对齐能力域、优先级、目标计分单元、端到端演示四项。
  3. 推送与 PR：Conventional Commits → `git push origin main`（SSH）失败则 `git push origin-https main`，各试一次即停 → 受保护 `main` 经 PR 合并 → 确认 CI S1–S4 全绿 → 记录 PR 与 issue 的 `Closes #x` 关联。
- **验收标准**：① 双轴报告含每轴发现数与最严重项；② 门禁套件结果行为 `passed` 全绿；③ PR 正文四节齐全且四项纳管字段齐全；④ 推送记录含实际使用的通道与结果；⑤ CI S1–S4 全绿；⑥ 3 轮未收敛时输出未收敛清单并停在本阶段。
- **阶段门禁**：B1–B8 全项；额外核对固定点、diff 非空、确认批次记录、PR 要素与检查名；推送失败时结论为 `BLOCKED` 并等待下次推送再试一轮。
- **学习要点**：交付前的最后一道语义闸门；「人工确认批次」与「最多 3 轮」体现可控收敛，而非无限返工。

## 5. 用于熟悉全流程的操作建议

1. **起点**：选 `attack-ai-agent`（攻击面最典型，已有 `docs/research/pyrit-native-api-attack-ai-agent.md` 与 issue #83 规格）跑一次完整 tracer bullet，再复制到 backlog 的 P1 条目。
2. **每阶段观察三件事**：输入来自哪里、输出被谁消费、门禁凭什么判定 `PASS`。三者可回答即掌握该阶段。
3. **对照阅读**：`docs/operations/pyrit-implementation-workflow.md` §3 保留 10 阶段历史映射，用于理解 PyRIT 对象映射；主线顺序以本文件为准。
4. **门禁留痕**：把每阶段的门禁记录表汇总到对应 issue，形成可回溯的全流程审计链。

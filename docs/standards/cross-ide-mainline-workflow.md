# 主线落地流程 · 完整方案（跨 IDE 通用版）

> **版本** v1.0 · **性质** 跨平台通用标准 · **状态** 生效
> **用途**：把一份 `SKILL.md`（或任何「能力声明文档」）落地为代码 / 可纳入 CI 的交付物。
> **与其他文档关系**：本仓库项目专属权威版见 `docs/operations/skill-mainline-workflow.md`；本文档是其**跨 IDE 可迁移的通用提炼**——剥离了平台绑定细节，保留统一流程、门禁与**提示词模板**，可直接迁入 Cursor / Cline / CodeBuddy / WorkBuddy / Aider 等任意支持 agent 的 IDE。
> **核心资产**：第 4 节的「调用方法 + 提示词模板」与第 8 节的模板总索引——这些是与平台无关的通用资产。
> **迁移必带（ADR-0005）**：把本流程迁入目标 IDE 时，必须同步 `AGENTS.md`「Token 预算纪律」**C1–C8** 到该 IDE 的 rules 文件，并接入 `scripts/check_token_budget.py --check`；仅复制 11 阶段流程视为迁移未完成。规范契约由 CI 静态层校验。

---

## 1. 核心原则

1. **顺序固定**：11 个阶段按编号执行；调换、合并、并行或跳过任一阶段均判为不符合项，须回到原顺序重跑受影响阶段。
2. **门禁闭环**：每阶段收尾执行 G0 协议，结论为 `PASS` 才进入下一阶段；`BLOCKED` 停留在当前阶段重跑全部检查项。
3. **行为单一真源**：`SKILL.md`（或等价能力声明）始终是行为唯一来源；规格只翻译、不改写。
4. **两遍 to-spec 不可合并**：阶段 2（行为规格 v1）与阶段 3（工程规格 v2 定稿）是不同产物、不同版本号，必须各自独立执行、独立留痕。
5. **提示词驱动**：每个阶段配有可直接复制的提示词模板（第 4 节）；agent 按模板执行，不依赖特定工具命令。
6. **可迁移性**：流程、门禁、模板与平台无关；仅「调用方式」外壳（如 slash 命令名、rules 文件位置）按目标 IDE 适配（见第 7 节）。

## 2. 完整流程概览（11 阶段一览）

| # | 阶段 | 一句话目的 | 主交付物 | 下游消费者 |
|---|---|---|---|---|
| 1 | `research` | 一手源核实实现依赖的事实 | `docs/research/<topic>.md` | 2、3、6、8 |
| 2 | `to-spec` ① | 行为规格 v1（做什么） | 规格 v1（issue，七节） | 3 |
| 3 | `to-spec` ② | 工程规格 v2 定稿（可验证/可拆解） | 规格 v2 定稿（同 issue 追加） | 4、6、8、9、10、11 |
| 4 | `to-tickets` | 工单拆解（垂直切片） | 父工单 + 子工单 + 依赖图 | 5、8 |
| 5 | `triage` | 定级（agent vs 人）+ brief | 标签 + agent brief | 8 |
| 6 | `codebase-design` | 模块边界与 seam 设计 | 设计记录 + seam 清单 | 7、8、9 |
| 7 | `domain-modeling` | 统一术语基准 | `GLOSSARY.md` / ADR 增补 | 8、9、10、11 |
| 8 | `implement-spec` | 按规格实现最小切片 | 实现代码 + 证据片段 | 9、10 |
| 9 | `tdd` | 红—绿—重构测试收敛 | 测试夹具 + 覆盖率 | 10、11 |
| 10 | `code-review` | 双轴代码审查 | 双轴报告 + 修复清单 | 11 |
| 11 | `pr-push-review` | PR + 推送前评审 + 双通道推送 | PR + CI 结果 + 推送记录 | 发布 |

**执行顺序（固定）**：

```
research → to-spec① → to-spec② → to-tickets → triage
        → codebase-design → domain-modeling → implement-spec
        → tdd → code-review → pr-push-review
```

**整体触发（唤醒词）**：说出 `/主线 [技能名]`（或 `全量落地` / `走全量` / `11阶段` / `完整流程`）即按上述顺序 1→11 自动推进，逐阶段过 G0。技能名缺省时询问目标，或默认 tracer bullet（本仓库为 `attack-ai-agent`）。**唤醒词强制包含 to-spec 两遍，不得合并或跳过。**

## 3. 阶段门禁协议 G0（通用基线）

每阶段收尾强制执行。门禁基线 B1–B8 为通用工程约束，下表给出**通用定义**与**本项目实例**（迁移时按项目调整）。

| 编号 | 通用基线 | 本项目实例（redteam-ai300） |
|---|---|---|
| B1 | 交付物结构合规，可通过结构校验 | 技能解剖五要素齐全；`validate_skill.py` 通过 |
| B2 | 术语与决策一致 | 术语以 `GLOSSARY.md` 为准；与 ADR 冲突须显式标注；`check_glossary.py` 通过 |
| B3 | 语法与构建 | 可编译/可构建；`unittest` 可发现并运行 |
| B4 | 证据契约 | 每步产出三件套（命令 + 输出 + artifact）；AI 交互有日志 |
| B5 | 证据与声明一致 | 提交值 == 报告/截图；访问证明同屏；技术读者可 copy/paste 复现 |
| B6 | CI 门禁 | 本地与 CI 判定一致；行覆盖率 ≥ 阈值（本项目 80%）；Conventional Commits；受保护分支仅经 PR 合并 |
| B7 | 依赖版本与对象图 | 锁定依赖版本（示例 `pyrit==1.1.0`）；禁用已废弃 API/对象 |
| B8 | 可追溯性 | 每条结论附一手来源；issue / PR / commit 互链；门禁记录留痕 |

**G0 收尾 5 步（每阶段必做）**：
1. 列交付物：逐项列出本阶段实际产出的文件、issue、命令与输出。
2. 逐项校验：对照 B1–B8 与本节「验收标准」逐条判定；可自动化的检查须给出确切命令与输出摘要。
3. 生成门禁记录表（字段固定）：编号 / 检查项 / 依据 / 实测结果（命令+输出摘要） / 判定 / 不符合项描述 / 修正要求 / 复验结果 / 结论。
4. 处置不符合项：结论 `BLOCKED` 时停留本阶段，按修正要求逐条改完并重跑本阶段全部检查项；结论 `PASS` 才进下一阶段。
5. 留痕：门禁记录写入本阶段交付物，并在对应 issue / 变更说明中留摘要。

**判定规则**：判定只取 `符合` / `不符合`；阶段结论只取 `PASS` / `BLOCKED`。「基本完成」「大体符合」不具判定效力。

## 4. 各阶段详细方案（调用方法 + 提示词模板）

> **调用方法约定**：
> - 整体触发：唤醒词（见 §2）一次性跑完全部 11 阶段。
> - 单阶段触发：在 agent 对话中直接说出阶段名（如「执行阶段 6 codebase-design」）或**直接粘贴下方对应提示词模板**。模板为自包含指令，粘贴即生效，不依赖平台。
> - 每阶段模板末尾均要求「完成后按 G0 收尾」，确保门禁闭环。

### 4.1 阶段 1 — `research`（调研）

- **目标**：用一手来源锁定实现依赖的事实（API 名称、版本、行为边界），消除规格阶段的猜测。
- **输入**：目标能力声明文档；官方仓库 / 官方文档 / 源码；现有调研索引。
- **输出**：`docs/research/<topic>.md`，逐条结论附来源 URL 与版本；含「已核实 / 待核实 / 已排除」三类清单。
- **验收**：①每条结论可定位到官方源；②版本号明确；③每条攻击/能力路径都有对应对象映射；④待核实项逐条命名且给出取证方式；⑤落盘于 `docs/research/`。
- **门禁**：B7、B8。
- **调用方法**：整体触发时自动首跑；单阶段说「调研 <技能名>」或粘贴模板。

```
【阶段1 research · 提示词模板】
你是资深软件开发工程师。执行阶段 1 research。
针对 <能力声明文档路径> 声明的能力，用一手来源（官方仓库 / 官方文档 / 源码）核实实现依赖的事实：
API 名称、版本、行为边界。逐项回溯到拥有该事实的源，记录版本破坏性变更与禁用名称，
标出实现前必须取证的核实闸。产出 docs/research/<topic>.md：每条结论附来源 URL 与版本，
含「已核实 / 待核实 / 已排除」三类清单。完成后按 G0 收尾（重点 B7、B8），结论 PASS 才继续。
```

### 4.2 阶段 2 — `to-spec` ①（行为规格 v1）

- **目标**：把能力声明翻译成「做什么」的用户视角描述（七节）。
- **输入**：目标能力文档；阶段 1 调研文档；术语表 `GLOSSARY.md`；triage / issue 约定。
- **输出**：issue tracker 中规格 v1（七节），标签 `ready-for-agent`；保留原文为行为唯一来源，不改写。
- **验收**：①七节齐全；②User Stories 覆盖全部攻击/能力路径与质量门；③术语符合 `GLOSSARY`；④与 ADR 无静默冲突；⑤Implementation Decisions 不含具体文件路径与代码片段；⑥seam 提案已与用户核对。
- **门禁**：B1、B2、B8。
- **调用方法**：整体触发时自动第二跑；单阶段说「to-spec 行为规格」或粘贴模板。

```
【阶段2 to-spec① · 提示词模板】
执行阶段 2 to-spec①（行为规格 v1）。读取 <能力文档> 与阶段 1 调研文档，
用领域术语撰写七节规格：
Problem Statement / Solution / User Stories（长清单）/ Implementation Decisions /
Testing Decisions / Out of Scope / Further Notes。
要求：User Stories 覆盖全部攻击/能力路径与质量门；Implementation Decisions 不得含文件路径或代码片段；
提出 seam（接缝）数量与位置并与我核对。发布到 issue tracker 并打 ready-for-agent 标签。
完成后过 G0（B1/B2/B8）。注意：本阶段只回答 What，出现代码块即越界。
```

### 4.3 阶段 3 — `to-spec` ②（工程规格 v2 定稿）

- **目标**：以 v1 为输入做第二次独立规格化，收敛为可验证、可拆解、可交接的定稿 v2。
- **输入**：v1 全文；阶段 1 待核实项取证结果；代码库现状；项目检查单（如 GOVERNANCE §8.2）；CI 门禁要求；依赖权威索引。
- **输出**：v2 定稿——在 v1 同一 issue 追加 `## 工程规格定稿 (v2)`，保留 v1 全文并附 v1→v2 差异清单（逐条理由）；若独立 issue 须双向互链 + 被取代标记。
- **验收**：①每条 User Story 有对应布尔验收条件；②每条验收条件指向具体检查命令或人工判据；③待核实项已关闭或转核实闸；④差异清单逐条可追溯；⑤不存在两套互相冲突的「当前规格」；⑥与阶段 2 内容不同且版本号递增。
- **门禁**：B1、B2、B6、B7、B8 + 上游复核（确认 v1 未被破坏）。
- **调用方法**：整体触发时自动第三跑，**必须与阶段 2 分开执行**；单阶段说「to-spec 工程规格定稿」或粘贴模板。

```
【阶段3 to-spec② · 提示词模板】
执行阶段 3 to-spec②（工程规格 v2 定稿）。以 v1 为输入做第二次独立规格化：
逐条审查 v1 User Stories 的「可判定性」，把不可判定的改写为布尔验收条件
（格式：给定 X，当 Y，则 Z 成立）；补齐 Testing Decisions（只测外部行为、列既有参考测试）；
把 CI 门禁映射到每条验收条件；收敛 seam 决策与对象图。
在 v1 同 issue 追加「## 工程规格定稿 (v2)」，保留 v1 全文并附 v1→v2 差异清单（逐条理由）。
完成后过 G0（B1/B2/B6/B7/B8 + 上游复核确认 v1 未被破坏）。本阶段是 to-spec 第二遍，不得与阶段 2 合并。
```

### 4.4 阶段 4 — `to-tickets`（工单拆解）

- **目标**：把 v2 拆成可独立交付、可并行判定的垂直切片（tracer bullet），显式声明依赖。
- **输入**：规格 v2；issue tracker 的 sub-issue / blocking 约定；既有工单编号。
- **输出**：父工单 + 每路径一张子工单 + 证据契约工单；每张含目标、验收条件、阻塞边、验证命令。
- **验收**：①每条 v2 验收条件至少被一张工单覆盖；②每张工单可单独验收；③阻塞边可查询；④标题术语一致；⑤无环形依赖。
- **门禁**：B2、B8。
- **调用方法**：整体触发时自动第四跑；单阶段说「拆工单」或粘贴模板。

```
【阶段4 to-tickets · 提示词模板】
执行阶段 4 to-tickets。把 v2 拆成可独立交付、可并行判定的垂直切片（tracer bullet），
每片保留一条端到端可运行链路。产出：父工单 + 每攻击/能力路径一张子工单 + 证据契约工单；
用 blocked-by（或回退文本 Blocked by: #n）声明依赖。每张工单含：目标、验收条件、阻塞边、验证命令。
校验：覆盖矩阵无空格、无环形依赖、标题术语与 GLOSSARY 一致。完成后过 G0（B2/B8）。
```

### 4.5 阶段 5 — `triage`（分类定级）

- **目标**：判定每张工单由 agent 还是人工承接，补齐 agent 就绪上下文。
- **输入**：全部新工单；五标签映射；PR-as-request 开关（可选）。
- **输出**：每张工单的规范标签、分类理由；`ready-for-agent` 工单的 brief（目标 / 输入 / 约束 / 验收 / 验证命令）。
- **验收**：①每张工单恰有一个规范标签；②每个 `ready-for-agent` 工单含完整 brief；③人工项与 `ready-for-human` 一一对应并记录依据；④结论留痕。
- **门禁**：B8。
- **调用方法**：整体触发时自动第五跑；单阶段说「triage 分类」或粘贴模板。

```
【阶段5 triage · 提示词模板】
执行阶段 5 triage。对全部新工单判定由 agent 还是人工承接。
按五标签状态机流转：needs-triage / needs-info / ready-for-agent / ready-for-human / wontfix。
需人工项（端点凭据、CI secrets、需手动交互）标 ready-for-human；信息不足标 needs-info 并列出所缺；
为 ready-for-agent 工单写完整 brief（目标 / 输入 / 约束 / 验收 / 验证命令）。
要求：每张工单恰有一个规范标签；ready-for-agent 必含完整 brief。完成后过 G0（B8）。
```

### 4.6 阶段 6 — `codebase-design`（模块与接口设计）

- **目标**：确定深层模块边界与 seam 位置，使实现可测试、可注入、对 agent 可导航。
- **输入**：规格 v2；工单；现有目录与边界；seam 提案（阶段 2 已确认）。
- **输出**：设计记录（模块职责、公开接口、依赖方向、seam 清单、注入点、对象图构造位置）。
- **验收**：①seam 数量与位置明确且与阶段 2 结论一致；②每个公开接口有职责/输入/输出/错误行为描述；③依赖方向单向；④测试替身可替换外部依赖；⑤与 ADR 冲突显式标注。
- **门禁**：B2、B7、B8。
- **调用方法**：整体触发时自动第六跑；单阶段说「codebase-design 设计」或粘贴模板。

```
【阶段6 codebase-design · 提示词模板】
执行阶段 6 codebase-design。确定深层模块边界与 seam 位置。
复用既有 seam，新 seam 压到最少并置于最高层；定义公开入口与可注入依赖；
明确外部依赖（如 PyRIT/外部服务）延迟导入与测试假后端策略；对象图统一采用当前版本 API（禁用已废弃对象）。
产出设计记录：模块职责、公开接口（含职责/输入/输出/错误行为）、依赖方向（单向）、seam 清单、注入点、对象图构造位置。
完成后过 G0（B2/B7/B8）。设计决定后续测试成本，接口要少、实现要深。
```

### 4.7 阶段 7 — `domain-modeling`（领域术语建模）

- **目标**：把实现引入的新概念纳入唯一术语基准，消除代码/规格/报告语义漂移。
- **输入**：规格 v2、设计记录、`GLOSSARY.md`、ADR 目录、实现层词汇清单。
- **输出**：`GLOSSARY.md` 增补；必要时新增 ADR；术语映射表（能力概念 ↔ 实现对象 ↔ 代码标识符）。
- **验收**：①映射表覆盖规格与设计中的全部新概念；②`GLOSSARY.md` 条目含定义与来源；③术语检查器通过；④ADR 编号连续、冲突显式标注。
- **门禁**：B1、B2、B8。
- **调用方法**：整体触发时自动第七跑；单阶段说「domain-modeling 术语」或粘贴模板。

```
【阶段7 domain-modeling · 提示词模板】
执行阶段 7 domain-modeling。把实现引入的新概念纳入唯一术语基准 GLOSSARY.md。
枚举新术语 → 与既有条目比对归一 → 为每个术语写定义、禁用同义词、来源 → 必要时新增 ADR →
产出术语映射表（能力概念 ↔ 实现对象 ↔ 代码标识符）。
运行术语检查器（如 check_glossary）须通过；与 ADR 冲突须显式标注。完成后过 G0（B1/B2/B8）。
```

### 4.8 阶段 8 — `implement-spec`（按规格实现）

- **目标**：按 v2 + 工单产出接口完整、可编译、可验证的最小实现切片，保持与行为声明一致。
- **输入**：规格 v2、`ready-for-agent` 工单与 brief、设计记录、`GLOSSARY.md`、依赖权威索引。
- **输出**：实现代码（模块、对象图构造、公开入口）、必要配置与依赖声明、每步证据片段；变更清单。
- **验收**：①每条 v2 验收条件有对应实现位置；②可编译/可构建；③对象图符合 B7；④每步证据三件套齐全且可 copy/paste 复现；⑤无硬编码凭据；⑥变更清单与工单一一对应。
- **门禁**：B1、B2、B3、B4、B5、B7、B8 全项。
- **调用方法**：整体触发时自动第八跑；单阶段说「implement-spec 实现」或粘贴模板。

```
【阶段8 implement-spec · 提示词模板】
执行阶段 8 implement-spec。按 v2 + ready-for-agent 工单与 brief 产出接口完整、可编译、可验证的最小实现切片。
外部依赖走注入点；每步产出证据三件套（命令 + 输出 + artifact），确保技术读者可 copy/paste 复现；
保持能力声明文档为行为唯一来源；无硬编码凭据；变更清单与工单一一对应。
完成后过 G0（B1/B2/B3/B4/B5/B7/B8 全项，门禁记录须含每条命令输出摘要）。本阶段只交付最小切片，完整测试在阶段 9。
```

### 4.9 阶段 9 — `tdd`（测试驱动开发）

- **目标**：以 v2 为判据补齐红—绿—重构循环，用测试锁定外部行为并收敛实现。
- **输入**：规格 v2 验收条件、阶段 8 实现、既有测试夹具、覆盖率要求。
- **输出**：新增/修订测试用例、证据契约夹具、红→绿→重构三轮记录、覆盖率数据。
- **验收**：①每条验收条件有对应测试；②红阶段有实际失败输出留痕；③全量测试通过；④业务代码覆盖率 ≥ 阈值（本项目 80%）；⑤只测外部行为，不断言实现细节；⑥本地与 CI 判定一致。
- **门禁**：B3、B4、B6、B8 全项。
- **调用方法**：整体触发时自动第九跑；单阶段说「tdd 测试」或粘贴模板。

```
【阶段9 tdd · 提示词模板】
执行阶段 9 tdd。以 v2 为判据补齐红—绿—重构循环：
为每条验收条件写一个失败用例（红）→ 最小改动使其通过（绿）→ 重构并复跑（重构）→ 补证据契约夹具。
只测外部行为，不断言实现细节。运行全量测试与覆盖率（业务代码覆盖率 ≥ 阈值，本项目 80%）。
测试暴露规格偏差时退回阶段 8 修正并重跑其门禁。完成后过 G0（B3/B4/B6/B8，附全量测试输出与覆盖率数字）。
```

### 4.10 阶段 10 — `code-review`（双轴代码审查）

- **目标**：相对固定基线，独立审查 Standards（编码规范）与 Spec（规格忠实度）两条轴，输出并列结论。
- **输入**：固定基线（如 `merge-base origin/main HEAD`）之后的 diff；规格 v2 与工单；编码规范、术语表、项目约定。
- **输出**：双轴并列报告（每轴发现数、最严重项、逐条分类：硬违规 / 判断项）、修复清单、复跑结果。
- **验收**：①两轴报告并列且各自结论完整；②每条发现带文件位置与分类；③硬违规数量为 0；④规格覆盖矩阵无遗漏；⑤门禁套件全绿。
- **门禁**：B1–B8 全项。
- **调用方法**：整体触发时自动第十跑；单阶段说「code-review 审查」或粘贴模板。

```
【阶段10 code-review · 提示词模板】
执行阶段 10 code-review。取固定基线（如 merge-base origin/main HEAD）之后的 diff，
并行独立审查两条轴：Standards（编码规范）与 Spec（规格忠实度），不合并、不重排。
逐条分类为硬违规 / 判断项；硬违规先修复并复跑门禁，判断项记录为改进项。
要求：两轴报告并列、硬违规为 0、规格覆盖矩阵无遗漏、门禁套件全绿。完成后过 G0（B1–B8 全项）。
```

### 4.11 阶段 11 — `pr-push-review`（PR 与推送前评审复合阶段）

- **目标**：完成推送前语义级双轴评审、PR 正文、双通道推送与 PR 创建，衔接 CI 门禁。
- **输入**：阶段 10 全绿结论、工作树与分支 commits、远端基线、规格 v2、PR 模板、双通道推送约定。
- **输出**：`pre-push-review` 双轴报告与门禁结果、`pr` 模板正文、PR 链接与编号、CI 状态、推送结果记录。
- **验收**：①双轴报告含每轴发现数与最严重项；②门禁套件结果全绿；③PR 正文四节齐全；④推送记录含实际通道与结果；⑤CI 全绿；⑥未收敛时输出清单并停留。
- **门禁**：B1–B8 全项。
- **调用方法**：整体触发时自动第十一跑（复合：pre-push-review → pr → 双通道推送）；单阶段说「pr-push-review 发布」或粘贴模板。

```
【阶段11 pr-push-review · 提示词模板】
执行阶段 11 pr-push-review（复合阶段，内部次序固定）：
1) pre-push-review：取远端基线 → 双轴评审 → 分类发现 → 按确认批次修复 → 复跑门禁（最多 3 轮收敛）。
2) pr：按模板写 PR 正文四节——Summary（最小可视化）/ Evidence（改前改后证据）/ Merge Danger（单向门/双向门与影响半径）/ 四项纳管字段。
3) 推送与 PR：Conventional Commits → 优先通道推送失败则转备用通道（各试一次即停）→ 受保护分支经 PR 合并 → 确认 CI 全绿 → 记录 Closes #x。
完成后过 G0（B1–B8 全项）。3 轮未收敛则输出未收敛清单并停留本阶段。
```

## 5. to-spec 两遍专项（重点）

### 5.1 为什么拆成两次

一次规格若同时承担「描述行为」与「定义验收」两职责会互相干扰：写行为时想"用户要什么"，写验收时想"怎么判定完成"。混写要么行为被验收细节污染（过早写实现/路径），要么验收含糊（无法判定）。主线把两职责拆成**两个独立阶段、两份独立产物、两次独立留痕**。

### 5.2 第一遍（阶段 2）步骤与七节模板

步骤：①探索代码库现状 → ②用领域术语撰写七节 → ③提出 seam 数量与位置并与用户核对 → ④发布到 issue tracker。

七节（每节写什么）：
- **Problem Statement**：要解决的真实问题 / 攻击场景。
- **Solution**：高层解法概述（不含实现细节）。
- **User Stories**（长清单）：每条用户视角的可观察行为，覆盖全部攻击/能力路径与质量门。
- **Implementation Decisions**：架构/技术选型方向，**禁止出现文件路径或代码片段**。
- **Testing Decisions**：测试策略方向（测什么、不测什么）。
- **Out of Scope**：明确不做的事。
- **Further Notes**：开放问题、风险、待核实项。

### 5.3 第二遍（阶段 3）步骤与布尔验收条件写法

步骤：①逐条审查 v1 User Stories 可判定性 → ②不可判定者改写为布尔验收条件 → ③补齐 Testing Decisions（只测外部行为、列既有参考测试）→ ④CI 门禁映射到每条验收条件 → ⑤收敛 seam 与对象图 → ⑥在 v1 同 issue 追加 v2 + 差异清单。

**布尔验收条件写法（模板）**：

```
给定 <前置条件/输入>，
当 <动作/触发>，
则 <可观测的判定结果，可为命令输出或人工判据>。
```

示例：`给定 一个合法的 prompt 输入，当 调用 attack 入口，则 返回结构化结果且不含未处理异常（断言：exit 0 且输出含字段 result）。`

### 5.4 两遍之间的衔接件（映射表）

既是 v2 的输出，也是阶段 4 `to-tickets` 的输入，是保持一致性的实体载体：

```
v1 User Story  →  v2 布尔验收条件  →  验证命令 / 人工判据  →  归属工单
```

无法判定为布尔条件的 v1 条目 → **回退阶段 2 澄清语义，不擅自改 v1 含义**（保证"内容不同但语义不冲突"）。

### 5.5 一致性四道锁

1. **行为单一真源**：`SKILL.md` / 能力声明文档只翻译、不改写。
2. **覆盖不冲突**：v2 覆盖 v1 全部路径；不存在两套互相冲突的「当前规格」（硬验收项）。
3. **差异可追溯**：v1→v2 差异清单逐条写理由。
4. **上游复核**：阶段 3 收尾重跑阶段 2 检查（B1/B2/B8），确认 v1 未被破坏。

## 9. 附录：术语与默认值

- **SKILL.md**：能力声明文档；本流程的行为单一真源。迁移时可替换为任意等价的能力/需求文档。
- **tracer bullet**：贯穿全链路的端到端最小可运行切片，用于验证架构与证据链。
- **seam（接缝）**：模块间可注入、可替换的依赖边界；阶段 2 提案、阶段 6 收敛。
- **G0 / B1–B8**：通用门禁协议，见 §3；非通用项（覆盖率 80%、`pyrit==1.1.0`、双通道推送等）为 redteam-ai300 实例，迁移时按项目替换。
- **唤醒词**：`/主线` · `全量落地` · `走全量` · `11阶段` · `完整流程`（后接可选技能名）。
- **默认值（本项目）**：tracer bullet = `attack-ai-agent`；覆盖阈值 = 80%；依赖 = `pyrit==1.1.0`；推送 = 双通道（优先通道失败转备用，各试一次即停）。

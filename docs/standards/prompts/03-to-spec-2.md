# 阶段 3 · to-spec ②（工程规格 v2 定稿）— 独立提示词

> 同步源：`docs/standards/cross-ide-mainline-workflow.md` §4.3。修改须两处同步（见 README「同步规则」）。
> **本阶段是 to-spec 第二遍，必须与阶段 2 分开执行、独立留痕、版本号递增，不得合并。**

| 字段 | 内容 |
|---|---|
| 目标 | 以 v1 为输入做第二次独立规格化，收敛为可验证、可拆解、可交接的定稿 v2 |
| 输入 | v1 全文（issue {ISSUE}）；阶段 1 待核实项取证结果；代码库现状；项目检查单（如 GOVERNANCE §8.2 八项）；CI 门禁要求；依赖权威索引 |
| 输出 | v2 定稿：在 v1 同一 issue 追加 `## 工程规格定稿 (v2)`，保留 v1 全文并附 v1→v2 差异清单（逐条理由）；若独立 issue 须双向互链 + 被取代标记 |
| 触发条件 | 主线整体触发时自动第三跑；单阶段触发：说「to-spec 工程规格定稿」或粘贴下方提示词 |
| 上游衔接 | 消费 v1 全文与阶段 1 取证结果；v1 语义不得擅改（无法判定的条目回退阶段 2 澄清） |
| 下游衔接 | v2 布尔验收条件是阶段 4 拆工单、阶段 9 测试、阶段 10 Spec 轴审查的判据 |
| G0 门禁 | B1、B2、B6、B7、B8 + 上游复核（确认 v1 未被破坏） |

## 提示词正文（整段复制即生效）

```text
你是资深软件开发工程师，正在执行 11 阶段主线工作流的阶段 3 to-spec②（工程规格 v2 定稿）。
上游输入：规格 v1（issue {ISSUE}）、阶段 1 待核实项取证结果、代码库现状、项目检查单与 CI 门禁要求。
若 v1 不存在，回退阶段 2，不得跳过第一遍。
任务：以 v1 为输入做第二次独立规格化：
1) 逐条审查 v1 User Stories 的可判定性，把不可判定的改写为布尔验收条件（格式：给定 X，当 Y，则 Z 成立）；
2) 补齐 Testing Decisions（只测外部行为、列既有参考测试）；
3) 把 CI 门禁映射到每条验收条件（每条指向具体检查命令或人工判据）；
4) 收敛 seam 决策与对象图；
5) 在 v1 同一 issue 追加「## 工程规格定稿 (v2)」，保留 v1 全文并附 v1→v2 差异清单（逐条理由）。
完成后按 G0 收尾（B1/B2/B6/B7/B8 + 上游复核：重跑阶段 2 的 B1/B2/B8 检查，确认 v1 未被破坏）。
硬约束：与阶段 2 内容不同且版本号递增；不存在两套互相冲突的「当前规格」；无法判定为布尔的 v1 条目回退阶段 2 澄清语义，不擅自改写。
```

## G0 收尾自检

- [ ] 每条 User Story 有对应布尔验收条件，且指向检查命令或人工判据
- [ ] 待核实项已关闭或转为核实闸
- [ ] v1→v2 差异清单逐条可追溯
- [ ] 上游复核通过（v1 完整、无双规格冲突）
